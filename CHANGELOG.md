# Changelog

Root-level changelog and version baseline for the standalone fork. The root version tracks the `pi-monorepo` workspace root; per-package changes continue to be recorded in `packages/*/CHANGELOG.md`. This file was created on 2026-09-20, after the repository was detached from the earendil-works/pi fork network (2026-09-19), to give the now-independent repo a single root version authority.

## [Unreleased]

### Changed

- **Sub-project `.pi` migrated from a symlink to a real directory with resource references** (2026-10-30 global rule revision). Why: the previous setup symlinked this repo's `.pi` wholesale to `~/Developer/FullStackEngineerAgent/.pi`, which conflated sharing with ownership — any file written into `.pi` here landed directly in the Agent project, polluting every sibling sub-project and showing up in that project's git history. Copying the resources instead was never an option either: `AGENTS.md` has no include mechanism, so a copy-based superset inevitably drifts from the Agent side. What changed: (1) the `.pi → ../FullStackEngineerAgent/.pi` symlink is gone, replaced by a real `.pi/` directory owned by this repo; (2) a new `.pi/settings.json` references the Agent project's `extensions` / `skills` / `prompts` / `themes` directories by path and keeps the same-named local directories (local resources are auto-discovered, so they need no settings entry); (3) the `AGENTS.md → ../FullStackEngineerAgent/AGENTS.md` symlink is unchanged, keeping the identity layer aligned rather than forked. Rule: this repo's `.pi/` is append-only (own resource directories, `.pi/APPEND_SYSTEM.md`); it must not restate or override the base rules, and project-specific rules go into `APPEND_SYSTEM.md` — never `SYSTEM.md`, which replaces the whole system prompt and would wipe out the agent identity. See `~/.pi/agent/docs/agents-registry.md`, section “智能体专属文件归属与子项目映射（2026-10-30 修订）”.

## [0.0.7] - 2026-10-23

### Breaking Changes

- Workspace package names dropped the `@earendil-works/` scope: `@earendil-works/pi-coding-agent` → `pi-coding-agent`, `@earendil-works/pi-ai` → `pi-ai`, `@earendil-works/pi-tui` → `pi-tui`, and the rest of the monorepo follows the same pattern ([#12](https://github.com/xhqing/pi-harness/issues/12)). Distribution stays on GitHub Releases (self-contained tarball and binaries); the unscoped names on the public npm registry are placeholder packages held by upstream, so the fork does not publish there. The `pi` command, `.pi` config directory, `PI_*` environment variables, and release asset names are unchanged.

### Added

- The editor now supports select-all (`super+a`, Cmd+A). With everything selected, `backspace` / `delete` clears the editor, typing a character replaces the whole text, and cursor movement, mouse clicks, or `escape` cancel the selection. macOS terminals intercept `Cmd+A` by default, so `docs/keybindings.md` and `docs/terminal-setup.md` document the pass-through configuration (Ghostty, iTerm2, kitty, WezTerm, VS Code) and the `tui.editor.selectAll` rebind fallback ([#10](https://github.com/xhqing/pi-harness/issues/10)).

### Changed

- **Repository renamed to `pi-harness`** (2026-10-18): the GitHub repository is now `xhqing/pi-harness` (renamed from `xhqing/pi`; old links redirect automatically), to set the fork apart from the upstream `earendil-works/pi` project. All repository URLs inside the repo were updated to the new name — README titles/badges/links (both languages), the LICENSE note, `FORK_RELEASES_URL` / `LATEST_VERSION_URL` in the update check and their tests, fork guidance in `package-manager-cli.ts` / `config.ts` / `interactive-mode.ts`, `DEVELOPMENT.md` / `MEMO.md` references, and the `repository.url` field of every workspace package (which still pointed at the upstream repo). Runtime identities are intentionally unchanged: the `pi` CLI command, the `.pi` config directory, `PI_*` environment variables, release asset names (`pi-coding-agent-<version>.tgz`) stay as they are. (The npm package names were unscoped separately on 2026-10-23, see below.)

- Mount the Agent-presence symlinks (2026-10-17 user revision): added `AGENTS.md → ../FullStackEngineerAgent/AGENTS.md` and `.pi → ../FullStackEngineerAgent/.pi` as relative symlinks and committed them to the repository. Under the new rule, agent-exclusive file entities live only in the responsible Agent project, while sub-projects mount these links so that a session started in the sub-project inherits the responsible agent's identity, rules and skills; the links dangle harmlessly when the repository is cloned in isolation.

### Fixed

- The footer now shows `(sub)` for API-key providers that declare subscription billing (`ApiKeyAuth.isSubscription`), so extension-registered plans no longer look like metered API pricing; the `kimi-coding` provider-name special case was removed in favor of the flag ([#9](https://github.com/xhqing/pi-harness/issues/9)).

- `ModelRuntime` availability refreshes publish in publication order instead of start order (a pass only publishes when newer than the last published pass and not started before the last state change), so concurrent passes no longer cancel each other and an awaited refresh cannot return a stale snapshot. This fixes the startup race that occasionally replaced the configured default model with a fallback model ([#11](https://github.com/xhqing/pi-harness/issues/11)).

- Refreshed the stale model references in the `packages/ai` tests after the upstream catalog removed several IDs; CI's `tsgo --noEmit` step is green again. Runtime assertions that only fail with the refreshed data (pricing and thinking-level maps) were aligned in the same pass.

- `packages/ai/test/zai-coding-plan-models.test.ts`: the GLM-4.6V China Coding Plan assertion now expects the refreshed upstream cache-read price (`cacheRead: 0.05`), which aligns the CI build (it hydrates `providers/data/*.json` from the upstream catalog at build time) and matches the upstream catalog-drift fix (earendil-works/pi `482c1381`). The assertion had pinned `cacheRead: 0`, so every CI run failed once upstream changed the value.

- `package-lock.json`: the root and workspace-root version fields are synced to `0.0.6` (they had drifted to `0.0.5` during the 0.0.6 version bump; `VERSION` and `package.json` were already `0.0.6`).

## [0.0.5] - 2026-10-12

### Changed

### Changed

The `workflow_run`-specific steps (skip-superseded-runs, docs-only skip) were dropped: on a manual dispatch the maintainer has already decided.
- `scripts/build-binaries.sh` and `.github/workflows/build-binaries.yml`: comments no longer reference the removed auto-rc pipeline (the build script's `repo_root` note now describes the relative-`--out` callers that broke).
- `TODO.md` / `TODO-archive.md`: archived **T4** as updated — the v0.0.3 stable release resolved its `releases/latest` pollution half (the pointer now serves v0.0.3); registered **T5** for the remaining update-chain gaps (prereleases never reach `latest`, so `pi update --self` cannot fetch an rc build; same-version re-releases need `--force`); also archived **T1** as completed — the chord `spliceItems` chunk-size fix (10,000 → 4,096, shipped in 0.0.3 via #2) restored the delta test suite to green (155/155 locally).

## [0.0.3] - 2026-09-29

First stable release of the standalone fork (the 0.0.3 baseline came from the root `pi-monorepo` package.json): the repository was detached from the upstream fork network, versioning was unified under the root `VERSION` file, update checks and self-updates now target the fork's own GitHub Releases, and an automated rc prerelease pipeline was added.

### Added

- Root `VERSION` and root `CHANGELOG.md` as the repo-wide version baseline.
- `scripts/build-npm-tarball.mjs`: self-contained npm-layout release tarball for GitHub Release distribution (inlines workspace packages and TUI native prebuilds, drops unpublished workspace dependencies).
- Bilingual README: `README_cn.md` alongside the English `README.md`.
- `TODO.md`: registered **T3** — repoint the version update check from the upstream pi.dev endpoint to this fork's own GitHub Releases and unify the version numbering (root `VERSION` 0.0.3 vs the upstream-inherited `package.json` 0.86.0 coexist; the upstream update banner misleads fork users, and `pi update` can overwrite the fork install with the official package).
- `packages/coding-agent/test/fork-version.test.ts`: new test-first coverage for issue #4 — the runtime package version (`packages/coding-agent/package.json`, re-exported as `config.ts` `VERSION`) must equal the repo root `VERSION` file, locking the "root VERSION is the single source of truth" acceptance criterion.
- `.github/workflows/auto-rc.yml`: automated prerelease pipeline — after the main-branch CI workflow completes green it derives the next `v<target>-rc.N` tag (target = root `VERSION` while unreleased, else patch+1), builds the full six-platform binary set plus the npm-layout tarball via `scripts/build-binaries.sh`, smoke-tests the linux-x64 build, and publishes a `--prerelease` GitHub Release with SHA256SUMS and commit-list notes. Rationale: dev-workflow's acceptance step expects prereleases to appear automatically as merges land on main, but this repo had no such supply channel — every rc had to be cut by hand. Skips superseded runs (main moved on while queued) and docs-only main states (nothing runtime-testable to install).
- `MEMO.md`: new low-frequency memo file — registered **M1** to periodically check whether upstream earendil-works/pi implements the editor select-all feature (fork tracking: #10). Our upstream proposal (earendil-works/pi#9949) was auto-closed under the new-contributor gate; the earlier same-scope request (earendil-works/pi#7038) was rejected by the maintainer with a Ctrl+G suggestion. Issue subscriptions only notify on thread activity, so a silent upstream implementation needs a periodic check.
- `TODO.md`: registered **T4** — the fork's update-check chain is polluted by the upstream-inherited v0.86.0 Release (`releases/latest` keeps pointing at it, so 0.0.3 installs are permanently told a newer version exists), and prereleases never enter the `latest` pointer (`pi update --self` cannot fetch rc builds). Discovered while wiring auto-rc.

### Changed

- Repository detached from the upstream fork network and now evolves independently: upstream community infrastructure removed (contributor/issue/PR/audit/model-catalog workflows, issue templates, `APPROVED_CONTRIBUTORS`, `CONTRIBUTING.md`), project guidance (`CLAUDE.md`) updated for standalone-fork positioning.
- The bundle build now copies TUI native prebuilds into `dist/bundle/native` and fails when one is missing; `@earendil-works/chord` is inlined instead of staying external.
- `packages/coding-agent/test/version-check.test.ts` and `test/package-command-paths.test.ts`: rewrote the update-check expectations for issue #4 ahead of implementation (tests red on the current upstream-pointing code): version-check requests must target this fork's GitHub Releases (`xhqing/pi`) with zero `pi.dev` traffic, response mocks use the GitHub `tag_name` payload shape, and `pi update --self` (installer-managed and npm-global paths) must either update from the fork's own source or disable with fork guidance — both Issue-sanctioned outcomes. Removed passthrough cases for `packageName`/`note` fields and the renamed-package self-update cases: GitHub release payloads carry neither field, so upstream's package-migration flow is unreachable from the fork's check source.
- Implemented issue #4: the update check now reads `https://api.github.com/repos/xhqing/pi/releases/latest` (tag comparison, semver-validated), `pi update --self` installs the fork's own release tarball (`pi-coding-agent-<version>.tgz`, newly shipped by the release workflow) instead of an npm registry spec, and installer-managed self-updates without `PI_INSTALLER_API_BASE` disable with fork guidance instead of contacting pi.dev. Version scheme unified: the internal `@earendil-works/pi-*`/chord workspace family (11 packages, enforced by the install-lock/shrinkwrap generators) moved from the upstream-inherited 0.86.0 to the root `VERSION` value 0.0.3; locks regenerated.

### Fixed

- `packages/chord` (`src/delta/index.ts` `spliceItems`): reduced the splice chunk size from 10,000 to 4,096 spread args — ~10k positional args sit at the V8 call-stack limit on macOS / Node 22 and made the large-append delta test fail stably in local full-suite runs (`RangeError: Maximum call stack size exceeded`). No behavior change beyond stack headroom; local `./test.sh` is fully green again ([#2](https://github.com/xhqing/pi/issues/2)).
- `scripts/build-binaries.sh`: moved the `repo_root` resolution from the npm-tarball step (line ~191) to the top of the script. The late `$(cd "$(dirname "$0")/.." && pwd)` ran after the script had already `cd`'d into the output directory, so a relative invocation (`./scripts/build-binaries.sh --out binaries`, exactly how `auto-rc.yml` calls it) resolved `./scripts/..` inside the output dir and died with `cd: ./scripts/..: No such file or directory` — the first auto-rc run (35707111801) failed on this instead of publishing `v0.0.3-rc.1`. Resolving once at the top (while `$0`'s relative path is still valid) and reusing the variable fixes any relative-invocation caller. Verified by a sandbox reproduction (old logic fails with the same error, new logic resolves correctly) plus `bash -n`.
- `.github/workflows/auto-rc.yml`: configured the `github-actions[bot]` git identity (`user.name` / `user.email`) in the tag-and-publish step. The second auto-rc run (35712627220) — after the `repo_root` fix, with all six platform binaries built and smoke-tested green — died at `git tag -a` with `Committer identity unknown` because runners carry no default git committer and the workflow never set one, so annotated-tag creation failed before the tag or the prerelease Release could go out. Setting the identity inside the only step that creates git objects keeps the fix scoped.
